# ADR 001: client event IDs are the idempotency boundary

## Decision

Every simulation event must include a stable `eventId` generated by the client. PostgreSQL enforces a unique constraint on the value.

## Why

Immersive clients can lose connectivity and retry requests. Checking for an existing ID in application code before inserting still leaves a race between concurrent requests. A database uniqueness rule makes the guarantee atomic.

## Behavior

The first submission returns `accepted: true, duplicate: false` and queues the event. A later submission with the same ID returns `accepted: true, duplicate: true` and does not queue another job.

## Tradeoff

The client must persist an event ID long enough to retry it. That is a reasonable requirement because the client already needs a local retry buffer for offline or unstable network conditions.
